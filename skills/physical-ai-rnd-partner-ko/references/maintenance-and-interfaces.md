# 변경 영향·인터페이스·복구

## 실제로 실행되는 기준부터 확인

실제 checkout/worktree·revision·기존 diff와 실행 중 프로세스/컨테이너/설정이 가리키는 경로를 필요한 만큼 확인한다. 디스크 파일을 바꿨다고 실행 중 서비스가 바뀐 것은 아니다. 과거 README와 현재 실행 상태가 다르면 증거와 시점을 구별한다. 사용자 변경과 기존 실패를 보존하고 새로운 회귀를 따로 보고한다.

공식 모델을 도입할 때 공식 설치·다운로드·체크포인트·예제 입출력을 먼저 기준으로 잡는다. 이미 완료된 재현은 근거를 확인해 재사용한다. 호환 패치는 실제 오류와 대상 버전에 맞게 최소화하고 차이를 설명한다. 설명·코드 검사만으로 공식 예제 실행을 완료했다고 하지 않는다.

대상 환경을 먼저 고른다. 로컬 편집→회사 GPU 실행→결과 회수라면 명령의 실행 위치, 대상의 실제 OS/드라이버/라이브러리·디스크·자원, 전송할 파일, 정상/실패 판별과 반환 결과를 연결한다. 로컬 설치가 원격 준비를 대신하지 않는다. 서버 접근이 안 되면 준비한 코드/명령과 미실행을 구별한다. 사용자별 경로나 GPU 구성을 범용 규칙으로 하드코딩하지 않는다.

## 모듈을 나누는 이유는 의미와 의존을 드러내기 위해서다

현재 구조를 우선 읽고, 변경이 필요한 경계에서 정책/알고리즘, 환경·장면, 센서·장치 어댑터, 평가·기록, UI의 책임을 구별한다. 모든 프로젝트에 새 계층·플러그인·대형 프레임워크를 도입하지 않는다. 순수 계산과 장치 I/O가 섞여 검증/교체를 어렵게 할 때 해당 경계를 분리하는 작은 변경을 검토한다.

새 인터페이스는 생산자·소비자와 대표 사용을 함께 읽는다. 크기와 타입 외에 물리적 의미를 확인한다.

| 경계 | 필요한 계약 |
|---|---|
| 인식/상태 추정→제어 | 대상/유효성, 단위, 기준 좌표와 변환 방향, 시각 도메인·최신성 |
| 관측→정책 | 관절 순서, 축·회전 표기, 전처리/정규화, 이력 순서, 누락 처리 |
| 정책→구동 | 행동이 토크/위치/속도/증분 중 무엇인지, 스케일·오프셋·클리핑·주기 |
| 환경→학습/평가 | reset, 종료/시간 제한, 최종 관측, reward, 성공 정의, 보조 개입 |
| UI/로그→사용자 | 현재 실행인지 기록인지, SIM/실물, 실제 측정인지 기준 표시인지 |

ROS 관례는 참고이지 모든 라이브러리의 실제 정의가 아니다. quaternion 성분 순서·변환 방향·정책 배열을 이름만으로 추정하지 않는다. 서로 다른 clock의 시각을 단순 차감하거나 replay/reset 뒤 과거 관측을 현재 입력으로 사용하지 않는다. 필요한 timeout과 제어 주기는 시스템에서 확인한다.

## 모델과 부속 자료의 호환성

actor 가중치만으로 실행 구성이 정해지지 않을 수 있다. 입력 정규화 통계·학습된 표현·캐시 latent·관절 매핑·보정·환경 자산이 어느 버전에 의존하는지 추적한다. 모델이 바뀌었다는 이유만으로 캐시를 전부 폐기하거나, 기존 캐시가 유효하다고 가정하지 않는다. 변경된 모듈, 생성 경로와 실제 소비자를 확인한다.

평가/학습 모드, 등록 buffer와 dropout/BN 동작, device·dtype도 관련 경로에서 확인한다. 일부 state_dict를 무시하고 로드할 때 누락·추가 key와 의도한 재사용 범위를 검토한다. 동작하지 않는 로딩을 strict=False로 감추지 않는다.

학습 재개, 일부 가중치로 새 실험을 시작하는 warm start, 추론 로드는 목적이 다르다. 재개하려면 optimizer·scheduler·RNG·replay·샘플러 등 그 알고리즘에 필요한 실제 상태의 저장/복원 범위를 확인한다. PyTorch 모델/optimizer 로드만으로 SIM 전체가 비트 단위 재개된다고 보장하지 않는다.

## 변경 영향과 회귀를 고른다

데이터·전처리·보정·정책·시뮬레이터·의존성을 바꾸면 어떤 입력과 소비자가 영향을 받는지 찾는다. 좌표 변환 수정은 알려진 입출력과 관련 통합 경로를, 정책 변경은 기존 능력/조건과 새 목표의 행동 평가를 선택한다. UI 변경 하나에 전체 학습을 요구하지 않는다.

원인 추적이 가능한 변경을 유지하고 큰 리팩터링·서식 변경은 기능 수정과 필요에 따라 분리한다. 실제 회귀를 정답 파일 갱신으로 덮거나 허용 오차를 조용히 넓히지 않는다. 버전 고정은 재현을 돕지만 노후화 비용도 있으므로 필요한 업그레이드를 별도 검증 가능한 변경으로 다룬다.

## 정상 기준으로 돌아가고 다음 사람이 이어갈 수 있게

코드와 함께 설정·모델/부속 상태·데이터/자산 식별·환경·실행 명령·결과 경로를 연결한다. 프로젝트가 이미 관리하는 immutable ID/manifest를 활용하며 매번 거대한 원자료 전체를 다시 해시하지 않는다. 재현 정보를 기록한 것과 실제 재실행에 성공한 것은 구별한다.

중요한 변경은 직전 정상 구성을 보존하고, 롤백이 영향을 주는 데이터·스키마·가중치·서비스를 확인한다. 파괴적 마이그레이션은 별도 범위를 확인한다. 장애 대응에서는 우선 영향과 증거를 보존하고 복구·원인 확인·재발 방지의 상태를 구별한다. 무관한 작업을 무차별 재시작하거나 같은 실패를 정보 없이 반복하지 않는다.

실제 장비 실행은 세션에서 허용한 대상·연결·동작·현장 조건을 따른다. 준비나 SIM 성공을 새 실물 동작의 허가로 확대하지 않는다. 첫 연결·변경된 제어 경계처럼 실제로 필요한 경우 현재 상태와 중지/복구 경로를 확인한다. 매 답변의 포괄적 승인 체크리스트로 만들지 않는다.
